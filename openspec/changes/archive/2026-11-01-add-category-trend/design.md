# Design

## Context

见 `proposal.md` 的 Why。设计只需要三件事的现状约束：

- 快照层是「一天一行」的存量模型：`asset_snapshot(day UNIQUE, total_amount, item_count, ...)`，`AssetStore.persistSnapshotForToday()` 是唯一写入点，`applyRemote` 是唯一的远端合并点。
- 同步是**按年分片的文件快照**（`snapshots-2026.json.deflate`），记录名 `snapshot-yyyy-MM-dd`，合并策略是整条 last-writer-wins。
- 图表层的折线横轴最终去掉了日期标签（见 D8），原先那套「按真实文字宽度反算刻度数量」的 `TrendAxis` 随之删除；柱状图的桶数反算保留同样的「按实际像素反算上限」思路。

## Goals / Non-Goals

**Goals:**

- 分类小计与总额**永远同一事务、同一时刻**写入，读取时不可能出现一新一旧。
- 分类/复合视图的横轴范围各自贴合自己的可用数据，不出现大片无数据空白。
- 柱状图在 393pt 宽度下每根柱子都有可见宽度，宁可少画几期也不压成发丝。
- 纵轴与横轴的空间收益靠**真实文字宽度**驱动，不靠魔法常量。

**Non-Goals:**

- 不做按比例倒推历史分类数据（proposal 已明确排除）。
- 不新增同步记录类型，不改分片策略，不改 LWW 合并语义。
- 不把历史记录列表改成分来源；它仍然是「每日总额」的流水。
- 不提供按**单个条目**（而非类别）切片的走势。

## Decisions

### D1. 分类小计用独立表，而不是给快照表加 7 列或塞 JSON

`snapshot_category(day TEXT, category TEXT, amount REAL, PRIMARY KEY(day, category))`。

- **为何不用 7 列**：类别集合来自 `AssetCategory` 枚举，将来增删类别就要 ALTER TABLE 并改动全部读写 SQL；列名还把枚举值固化进 schema。
- **为何不用 JSON 列**：分类归并要按类别分组求和，JSON 需要全部读进内存再解，SQL 层无法过滤与聚合，且校验「合计等于总额」得先解码。
- **为何不建外键到 `asset_snapshot`**：快照是墓碑删除（`deleted_at`），不是物理删除；外键 `ON DELETE CASCADE` 在墓碑模型下等价于没有。级联由写路径显式完成（见 D2）。

### D2. 每天写全 7 行，含 0；覆盖而非累加；快照墓碑时一起清

- 写全 7 行（含 `0`）：读取时不需要「向前回溯最近一次非零值」，某类别被清空后曲线能直接落回 0。成本是 7 行/天 ≈ 2555 行/年，对 SQLite 可忽略；deflate 后同步体积几乎不变。
- 覆盖语义：写当日快照时先按 `day` 删除该日全部分类行，再批量插入当前值，与 `asset_snapshot` 在**同一个事务**里完成。用 DELETE+INSERT 而不是 UPSERT，是为了让「某类别这次不该存在」不会残留旧行——虽然当前总是写全 7 行，这条规则让写路径在类别集合变化时仍然正确。
- 墓碑：`deleteSnapshot` / `deleteAllSnapshots` 同时删除对应日期的分类行。分类行自身不带 `deleted_at`、不参与同步的独立推送。

### D3. 分类明细内嵌进当天的快照记录，字段级不做合并

`SyncRecord.snapshot` 增加一个 `categories` 字段（`[类别 rawValue: Double]`），随整条记录 LWW。

- **为何内嵌**：分类明细与总额的生命周期完全一致，拆成独立记录会让推送、拉取、冲突处理的代码路径翻倍，还会出现「总额来自 A 设备、分类来自 B 设备」的错配。
- **为何不做字段级合并**：分类小计与总额必须自洽（合计 = 总额）。字段级合并两个设备的半份数据，结果一定不自洽。
- **兼容性**：`SyncRecord.fields` 是字典，旧版本读到多余字段会忽略；新版本读到没有该字段的旧记录，按「该日无分类明细」处理，不抛错、不当作 0。

### D4. 归并层区分「没有基准」与「变化为零」

新增 `CategoryTrendAggregator`，输出 `CategoryTrendPoint { date, category, value, delta: Double? }`：

- `value`：该类在桶内**最后一条**记录的值（与总资产曲线同一套桶规则，`TrendAggregator` 的 `period.bucketStart` 与 `maxPoints` 直接复用）。
- `delta`：与该类**上一个存在的桶**相减；第一个桶为 `nil`，不是 `0`。

这个 `nil / 0` 的区分是柱状图正确性的关键：`nil` 表示没有比较基准（不画柱），`0` 表示确实没动（画一根 0 高的柱，配合列表的「持平」）。用 `Double` 并在渲染时判断 `!= 0` 会把两者混为一谈。

### D5. 复合柱状图：柱高是变化量，颜色是类别身份

- 柱高 = `delta`，零轴上下即涨跌；柱色用 `AssetCategory.tint`。
- **为何不把柱子画成红涨绿跌**：分组柱里颜色是**身份编码**，一旦颜色兼职表达涨跌，图例就失效（7 根同色柱无法分辨类别）。涨跌的红绿语义放在下方列表——那里是文字，不存在歧义。
- **已知副作用**：`股票` 的类别色恰好是红色，一根向下的红柱可能被一眼读成涨。缓解：零轴线加重、负值柱端点描边，并在图例中固定「股票在第一根」的位置顺序。

### D6. 桶数与类别数按宽度反算，不足时先减桶、再合并类别

```
groups = 实际有数据的类别数
每根柱最小 5pt，桶内间隙 1pt，桶间间隙 8pt
maxBuckets = floor(plotWidth / (groups * 6 + 8))
下限 5 个桶；若 maxBuckets < 5，则按「本周期变化绝对值」取前 5 个类别，
其余合并为「其他」，再重算一次
```

- 与横轴刻度收敛同源：都是「按实际可用宽度反算上限」，不是估算常量除以估算宽度。
- 复合视图的「本周期」定义就是收缩后的这几期，列表与 footer 文案必须使用同一个数值，不允许图说 8 期、列表算 30 期。

### D7. 视图切换用 Menu，不用 Segmented

候选项 9 个（总资产 + 复合 + 7 类别），393pt 下 segmented 会截断。Menu 带勾选态，放在 Section header 右侧，与现有「单位：万」同一行。

### D8. 绘图区：四个来源，一个禁区

| 手段 | 做法 | 收益（393pt 估算） |
|---|---|---|
| 行内边距 | 图表行 `.listRowInsets(EdgeInsets())` | +32pt 宽 |
| 纵轴标签 | `AxisValueLabel` 自定义为整数文本 | 约 +10pt 宽 |
| 高度 | 240 → 300 | +25% 面积 |
| 横轴标签 | 整个去掉日期文字，只留网格线 | 两端不再为「放得下标签」留白，竖向省下一行标签高度 |

禁区：`chartPlotStyle(padding:)`——项目已知的坑，它只移动数据区、纵轴刻度不动，会导致曲线整体相对刻度偏移（见 `openspec/config.yaml` 的「已知的坑」）。

**联动细节**：`plotWidth` 现在写死 `chartWidth - 64`，纵轴改成整数标签后这个常量偏大，会让刻度数偏保守。改为 `chartWidth - 52` 并**加注释说明它是估算值、估小了只会少放一个刻度、估大了才会截断标签**，保留原有的「宁可少放」取舍。

### D9. 空状态要说出起点，不画假线

`AssetStore` 暴露 `categoryTrackingStartDay: Date?`（分类表的第一天）。分类视图没有数据、或复合视图不足两期时，显示「分类明细自 `yyyy-MM-dd` 起记录」，而不是画一条 0 值曲线或一个空坐标系。

### D10. 演示数据同步生成分类拆分

`seedDemoHistoryIfNeeded` 目前只写总额。需为每条演示快照生成 7 类拆分（比如 股票 60% / 基金 20% / 现金 15% / 其他 5%，带小幅扰动），否则复合视图在 `--seed-demo-history` 下永远是空的，无法验收。

### D11. 长历史用「滑动窗口」，窗口决定纵轴与统计

- **载入上限与显示上限分开**：`StatsPeriod.maxPoints` 只表示「最多归并多少历史」（日 730 天），
  与屏幕上同时能看到多少无关；一屏的上限是 `StatsPeriod.visiblePointLimit`（90）。
  早先把两者当成一回事，结果历史一超过一个月就再也看不见。
- **窗口逻辑抽成 `TrendWindow`**（纯值类型）：是否显示滑条、默认偏移、越界夹紧、按偏移切一屏都在这里，
  视图只负责把 `Slider` 接到 `offsetBinding` 上。
  抽出来的理由是**拖动本身在无图形界面的模拟器里点不了**，只有纯逻辑能写测试。
- **翻页用独立滑条，不用 `chartScrollableAxes`**：后者的横向拖动会和 `chartXSelection` 的长按选点抢
  同一个手势——想翻页变成弹出气泡，想选点又滑走了。滑条还有一个好处：能精确停在某一段。
- **纵轴与区间统计跟着这一屏**：不跟着全量走。代价是滑动时纵轴会重新定标，
  所以域取「首尾刻度」并且刻度吸附到 1/2/5×10^k 的步长，跨格才变，不会每帧呼吸。
- 备选：纵轴固定为全量范围 → 不抖动，但早年 8 万的旧数据会把当前 15~20 万的曲线压成贴顶一条线，
  等于把「看变化」这个目的废掉。

### D12. 图表卡片左侧做成直角（把图表挪到 section header）

- **问题**：`insetGrouped` 的 section 会对 body 里的每一行做圆角裁切，而纵轴数字正好长在左上、
  左下两块圆角里。加行内边距只是「躲」，尺寸一变又会被啃。
- **试过但无效**：`listRowBackground` 换成 `UnevenRoundedRectangle`（左直角）、
  行内自绘背景 + `listRowBackground(.clear)`——两者都会被 section 的裁刀切回圆角。
- **有效解法**：把图表挂到 **section 的 header** 上，header 不属于卡片、不受裁切，
  再自己画一块四角直角的底（起初只削左角、右侧留圆角，后来也一并削平：一边方一边圆看着是歪的）。顺带发现 Charts **不会把自己裁进 frame**，
  面积填充会溢出到框外——以前被 List 的裁切盖住了，挪出来后必须显式 `.clipped()`。
- **代价**：header 自带的内边距比卡片多约 20pt（440pt 宽实测：header 内容 40…400，卡片 20…420），
  需要用负 padding 补回来才能与其他卡片对齐；这个数值随系统样式变化，换 list 样式或 iPad 分栏时要重新量。
- **顺序有坑**：负 padding 只把**内容**撑大，视图对外报的尺寸仍是没撑开的那一份。
  因此 `.background` 必须加在负 padding **之前**，否则底色按没撑开的尺寸绘制，
  内容（纵轴数字、面积填充）会从卡片两侧各漏出约 7pt 与 5pt，看上去像「曲线跑到卡片外面」。
  现在顺序是 `内容 → .background(Rectangle) → .clipShape(Rectangle) → .padding(.horizontal, -20)`。
- **四角一致**：只削左角时，右边那两处圆角在视觉上把整块拉歪了；四角都直之后卡片像一块干净的画布，
  代价是与同页其他圆角卡片风格不一致——这是刻意的，图表的可读性优先。

## Risks / Trade-offs

- [分类明细起点晚于总资产，用户误以为数据丢失] → 空状态与 footer 明写起点日期；切换视图时横轴贴合各自范围，视觉上「短」就有了合理说明。
- [日粒度下多数桶为 0，柱状图稀疏] → 属于真实状态，不偷偷改粒度；footer 说明「未改动的期为空柱」。
- [分类合计与总额不自洽] → 同一事务写入 + 单元测试断言 `sum(category) == total`；`applyRemote` 合并后也断言一次，失败则记 `lastErrorMessage` 而不静默。
- [7 类同桶导致柱宽不足] → D6 的减桶/合并两级降级；合并为「其他」时列表里该行标注「含 N 个类别」。
- [旧版本客户端写入的快照没有分类字段] → D3 的兼容规则：视为该日无分类明细，图表跳过而不补 0。
- [纵轴整数标签牺牲精度] → 数值精度由长按气泡（一位小数）与列表承担，纵轴只承担刻度定位。

## Migration Plan

1. `AppDatabase` 增加 `schemaV3`，`CREATE TABLE IF NOT EXISTS`，`user_version` 2 → 3，**不回填**历史分类。
2. 写路径：`upsertSnapshot` 扩展为同一事务内「写快照 + 重写当日分类行」。这是唯一写入口，`recordSnapshotForToday` 与每次条目改动都会经过它。
3. 读路径：`fetchSnapshots` 一次性把分类行读成 `[dayKey: [category: amount]]` 再挂到快照上，避免 N+1 查询。
4. 同步：`SyncRecord.snapshot` 增加字段；`fetchDirtyRecords` 组装、`applyRemoteSnapshot` 解包并写分类表；演示数据标记为已同步的逻辑不变。
5. 视图：先落横轴格式与绘图区（纯视图，可独立验收），再落视图切换与柱状图。
6. 回滚：旧版本代码不读新表；同步记录里多出的字段被字典忽略；`user_version` 只增不减，旧版本启动时不会因为版本更高而报错。无需数据回退脚本。

## Open Questions

- 复合模式在「日」粒度下是否默认切到「周」聚合，属于默认值取舍，不影响 spec 与实现路径，可以等实际使用过一段时间再定。
