## Context

动机见 `proposal.md` — Why；行为契约见 `specs/`。

落地时面对的约束：

- **数据量极小、形状固定**：几条到几十条资产条目，加上每天一条快照（一年 365 条）。没有查询复杂度，也没有并发写入压力。
- **改动点集中在少数几个写操作**：条目增删改排序。所有快照逻辑都可以挂在这一个入口上。
- **需要跨设备一致，但用户可能没开 iCloud**：同步必须是增强能力，不能成为 App 可用的前提。
- **iOS 18.0+、无第三方依赖**：工程由 `project.yml` 经 xcodegen 生成，依赖只有系统框架（SwiftUI / Swift Charts / sqlite3）。
- **同步的传输层无法在本机自动化验证**：真正的跨设备 iCloud 往返需要登录 iCloud 的真机。这是本设计里最重要的一个约束——它直接决定了架构必须把「传输」和「合并逻辑」切开。

## Goals / Non-Goals

**Goals**

- 让「每次改动都记录当日总资产」成为不可绕过的契约：所有写操作走同一个入口，不存在漏记的路径。
- 让同步的**合并语义**（冲突裁决、删除传播、离线容错、增量跳过）完全可自动化测试，不受传输层是否可测的影响。
- 让 iCloud 不可用成为**良性降级**而不是错误：本地数据一个字都不动，改动保留待补传。
- 让出问题时能自证：同步每一步都有日志，设置页有诊断面板。

**Non-Goals**

- 不追求实时同步。触发点是启动、回前台、本地改动后去抖、以及云端变化通知；秒级延迟可以接受。
- 不做多用户 / 共享账本。同步范围是同一个 Apple 账号下的私有数据。
- 不做历史快照的手工编辑或补录。快照是当前状态的派生结果，不是独立录入的数据。
- 不做按年的数据裁剪或归档。按年分片已经保证单文件体积有上界，裁剪留待将来。

## Decisions

### 1. 直接用 sqlite3，不用 Core Data / SwiftData

数据模型只有两张表、几个字段，查询是最朴素的 `SELECT ... WHERE deleted_at IS NULL`。Core Data 会引入模型文件、上下文合并、迁移栈，而 SwiftData + CloudKit 还有额外约束（要求可选关系、不支持唯一约束等），与「按自然日唯一」这一核心约束直接冲突。

**代价**：需要自己写建表、迁移与 SQL 绑定。实际约 200 行，且换来的是：schema 完全显式、`UNIQUE(day)` 这样的一致性约束可以直接交给数据库、迁移就是 `PRAGMA user_version` 加 `ALTER TABLE`。

### 2. 快照用「自然日唯一键 + upsert」表达，而不是「一天一行流水」

`asset_snapshot.day` 上加 `UNIQUE`，写入统一走 `INSERT ... ON CONFLICT(day) DO UPDATE`。这样「同一天只保留最新值」是**数据库层面的保证**，而不是应用层的约定——漏写一次判断也不会产生重复行。

配套地，`recorded_at` 在 upsert 时刻意不被覆盖，`updated_at` 每次刷新。这样「当天是否被修改过」是可查的。

### 3. 曲线归并取桶内「最后一次记录」

周 / 月 / 年的桶里有多条日快照时，取时间上最后一条的值。理由：快照是**存量**，不是流量。取平均或求和都会得到一个不表示任何真实时点的数字，而取最后一次等于「该周期结束时的资产状况」，是用户唯一能对应到现实的解释。

### 4. 曲线气泡挂在数据点上，按相对高度决定朝上还是朝下

最初把气泡挂在 `RuleMark` 的 `.annotation(position: .top)` 上，结果它被放在绘图区上方、超出 `Chart` 的 `frame` 而被裁掉。第一次修复用 `.chartPlotStyle { $0.padding(.top, 64) }` 给顶部腾空间——**这是个错误**：它只把数据区下移，纵轴刻度与标签不跟着动，导致曲线整体相对刻度偏移。实测 19.91 万的点被画到了 16.7 万的位置。

最终做法：气泡挂在**被选中那个数据点的 `PointMark`** 上，并根据该点在纵轴上的相对位置（`> 0.55` 则朝下）选择 `.top` / `.bottom`。这样既不需要改绘图区几何，气泡也永远落在绘图区内。

**明确记录：不要再用 `chartPlotStyle` padding 来给气泡腾地方。**

### 5. 气泡用固定浅灰而不是 `.regularMaterial`

`.regularMaterial` 会跟随背景解析颜色，在深色环境下变成深色底，与黑色文字叠加后不可读。改成固定的 `Color(white: 0.96)` + 黑色文字 + `strokeBorder`，在浅色与深色模式下表现一致。

### 6. 同步走 iCloud 云盘文件，不走 CloudKit，也不走键值存储

三条路线都实际走过：

| 方案 | 结果 |
| --- | --- |
| CloudKit（自定义 zone + 记录） | 需要服务端 recordType schema，正式环境要手动 Deploy；任何对不上都是 `CKError 15 serverRejectedRequest`，且错误里不带原因。已放弃。 |
| `NSUbiquitousKeyValueStore` | 能用，但 1MB 是**所有键共享的总配额**，拆键不能规避。已放弃。 |
| iCloud 云盘文件（ubiquity container） | 无总容量上限，可按年分片，单文件体积天然有上界。**采用**。 |

分片的具体收益在 `specs/icloud-sync/spec.md` 里已是可验证契约（只重写改动那一年、单年文件体积有上界）。

### 7. 删除用墓碑而不是物理删除

如果本地直接删行，离线设备再上线时只能从「记录已消失」推断，而**没有时间戳可以参与冲突裁决**，「删除」与「另一台设备后来的修改」谁更新就无法判断。改成写一条 `deleted = 1` 且带新 `updatedAt` 的普通记录后，冲突裁决对删除和修改是同一套规则。

### 8. 先推后拉，且只有整轮成功才推进文件指纹索引

先推可以让本地新改动尽早到达云端；随后拉取会用同一套 `updatedAt` 规则裁决，若云端更新则本地被覆盖（符合语义）。索引只在整轮成功后写入，避免中途失败后跳过本应重读的文件而漏数据。

### 9. 启动不自动写入示例数据

iCloud 数据是**异步回灌**的：系统可能在 App 读完本地之后才把远端内容送过来。只要启动就播种，重装 App 时「本地新播的示例条目」与「同步回来的旧条目」标识不同、无法去重，必然重复（实测：股票与流动资金各两份，总资产从 11.80 变成 26.10）。

改为空状态下的显式按钮，且只在列表为空时生效。

### 10. 传输层抽象成协议，合并逻辑放在协议之外

`SyncTransport` 之上是 `SyncEngine`（推拉顺序、冲突裁决、脏标记），之下是具体存储。生产实现是 `FileSyncTransport`，测试里换成内存 / 本地目录实现。同样地，文件存储抽象为 `CloudFileStore`。

这是为了绕开「真机 iCloud 无法在 CI 里验证」这一约束：**合并语义可以百分之百被单元测试覆盖**，留下来的未验证面只有系统 API 调用本身。Debug 下的 `--use-local-sync-directory` 进一步让完整的文件链路能在模拟器上跑通。

### 11. 所有跨进程等待都设超时

CloudKit 的 `accountStatus()` 在异常环境下被实测为**永不回调**，界面会永久停在「正在同步…」且按钮变灰。现在账号查询 8 秒超时、整轮同步 40 秒超时。用 `ResumeOnce` 保证续体只被恢复一次，超时后不再等待原操作。

## Risks / Trade-offs

- **跨设备同步无法在本机自动化验证** → 合并逻辑全部下沉到可测的协议之上；文件存储抽象为 `CloudFileStore`，并用 Debug 开关在模拟器上跑通完整文件链路。残留风险：iCloud 容器在你的账号下建不出来、或云盘的按需下载行为异常。
- **`updatedAt` 依赖设备墙钟** → 两台设备时钟严重偏差时，LWW 会做出错误裁决。个人记账场景下可接受；若将来需要，可换成设备序号 + 逻辑时钟，但那会改变规格。
- **云盘文件是「读-改-写」，不是原子追加** → 两台设备几乎同时写同一年文件时，存在丢失一次更新的窗口。缓解：写入前先读并合并，且每台设备在本地仍保留完整数据，下一轮同步会把落后的一方重新推上去。
- **`ubiquityIdentityToken` 作为账号信号** → 它反映的是「能否访问 ubiquity 容器」，不保证云盘一定在同步。因此它只用于界面展示与「本轮是否值得尝试」，不作为正确性依据。
- **墓碑会长期保留** → 删除的条目会留下一条永久记录。规模上可以忽略（个人条目数量级）；如果将来需要清理，需要一个「墓碑保留窗口」的规格，届时再单独立项。
- **`NSData.compressed(using: .zlib)` 输出的是 raw DEFLATE** → 不是 gzip，没有 gzip / zlib 头，`gunzip` 解不开。文件后缀因此定为 `.json.deflate` 而不是 `.json.gz`，避免误导。
- **按年分片意味着跨年查询要读多个文件** → 曲线的「全部年份」视图会读取全部年份文件。以一年几 KB 计算，即使十年也只有几十 KB，可接受。

## Migration Plan

- 这是工程的第一批规格，本地数据库从空库建起；`PRAGMA user_version` 已支持后续迁移（v1 建表，v2 增加同步所需的 `deleted_at` / `sync_dirty` 与 `sync_state`）。
- 同步的启用需要一次性配置：填入 `DEVELOPMENT_TEAM`、在 Signing & Capabilities 勾选 iCloud Documents。配置完成前 App 按纯本地模式运行，不存在「半同步」状态。
- 回滚：关闭设置页的同步开关即可退回纯本地；数据库结构不因关闭同步而改变。

## Open Questions

- 是否需要同步的实时性提升（例如更积极地利用云盘变化通知）。当前触发点在个人使用下已经足够，且不影响规格。
- 墓碑是否需要保留窗口。当前不清理，规模上无压力。
